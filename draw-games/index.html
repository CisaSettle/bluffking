彩票与骰宝：公开过程，独立复核

draw-games/ 是现有 BluffKing 开源仓库的子目录。这里公开开奖输入、确定性抽样、中奖计算、购票封盘及相关持久化代码，并提供无需连接 BluffKing 的离线验证器。覆盖骰宝、刮刮乐、双色球、快乐8、福彩3D、大乐透和 TOTO；奖项与金额均为练习豆。

本版本的证明协议尚未部署到生产。公开源码不等于线上已切换协议。生成这些证明需要配套版本的后台与客户端；开源标签不证明生产正在运行对应二进制。没有证明的历史记录明确保留为旧记录，不会补造承诺。

代码采用根目录的 AGPL-3.0-only 许可证，品牌规则见 商标说明。仓库不含玩家数据、运行密钥、未揭示种子或未来实际开奖结果。

三种开奖流程

游戏开奖前开奖后及边界
骰宝房间每轮固定服务器种子承诺，持久化后才能接受投注；投注请求绑定该承诺。成功的 HTTP 投注确认等待该投注持久化。公布种子并重算三颗骰子。WebSocket 展示可能早于持久化确认；确认超时表示结果未知，不能当作撤销。房间没有玩家种子，运营方预先知道结果，且承诺本身不能阻止事先筛选种子或中止一轮。
刮刮乐、单人骰宝先取得持久化的服务器种子承诺，再由浏览器安全随机生成 32 字节玩家种子。请求绑定承诺、玩家种子和购买／投注条件，浏览器在请求前保存回执。公布服务器种子后，可重算结果及兑奖。刮刮乐单张全部揭示后才公开完整种子；5／10 张批量购买直接揭示。服务器收到玩家种子后能够计算结果，承诺不能强制其继续服务或支付。
双色球及其他定期开奖游戏、期号、协议版本、封盘时间、drand 链和未来轮次组成固定计划。购买请求须回传已看到的计划承诺，票据保存同一计划。验证指定轮次的 BLS 签名，按公开算法生成号码。没有可选择的服务器种子；只等待已选轮次，不因服务异常换轮次或改用系统随机数。即使运营方不提供结果，持有相应公共信标仍可自行重算。

定期开奖的固定输入

双色球、大乐透、TOTO 每 5 分钟一期，大乐透错开 75 秒，TOTO 错开 150 秒；快乐8 每 2 分钟，福彩3D 每 3 分钟。所有这些游戏在计划开奖前 5 秒封盘，期号标签使用新加坡时间。计划选择在开奖时间或之后的第一轮 drand quicknet 信标，而不是请求时的“最新轮次”。

固定链标识为 52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971，起始时间为 Unix 秒 1692803367，每轮 3 秒。beacon.rs 固定公钥并验证 bls-unchained-g1-rfc9380 签名；随机输入是 SHA-256(signature)，不信任 HTTP 响应自带的随机数字段。

lottery.rs 将计划承诺与信标随机输入绑定；proof.rs 定义带域区分、长度前缀的 SHA-256 输入和计数器流。范围抽样使用拒绝采样消除取模偏差，无放回抽样使用部分 Fisher–Yates。信标网络仍有门限参与者、时钟与可用性假设，详见 drand 安全模型。签名验证使用固定版本的 drand-verify 0.6.2。

后台在数据库事务与行锁之外进行有超时、响应大小上限和重试间隔的信标请求。无法取得或验证指定信标时，同一期继续待开奖；已公开计划与已完成结果受持久化约束保护，恢复与重试不另选结果。旧期只按原流程完成结算，保持无证明标记。

独立复核

从公开仓库根目录构建独立验证器。首次构建可能下载锁定依赖；运行验证器不联网，不需要数据库或 BluffKing 账号。

cargo build --locked --manifest-path draw-games/verifier/Cargo.toml
./draw-games/verifier/target/debug/draw-verify proof.json
./draw-games/verifier/target/debug/draw-verify proof.json --receipt pre-draw-receipt.json
  1. 在配套客户端投注前保存承诺回执；开奖后下载证明。客户端可导出 {proof, receipt} 文件；也可分别提供证明与先前保存的回执。
  2. 验证器重算号码或骰子，并在证明包含投注／票据信息时复核成本与奖金。提供回执时还会比对原承诺、玩家种子及相应投注条件。
  3. 成功输出 outcome: "replayed"；有相符回执时为 receipt_match: "matched"，未提供时为 "not_provided"。不匹配或证明损坏会输出 "rejected" 并以退出码 1 结束。仅重算成功不代表拥有开奖前的证据。

定期开奖提供无需账号的 GET /api/draws/:game/:period/proof，返回 plan、proof 和 proof_status；状态为 pending、available 或 legacy。这里不公开个人选票与账号信息。游戏历史中的个人票据可合入证明的 ticket 字段，用于核对中奖计算。

若运营方不提供开奖证明，从既定链的 https://api.drand.sh/52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971/public/{round} 取得计划中的准确轮次，保存为 beacon.json，再运行以下命令。把 GAME 和 PERIOD 换成已保存计划中的游戏名和整数期号；命令检查轮次及签名，再输出可复核的完整开奖证明。

./draw-games/verifier/target/debug/draw-verify --derive-lottery GAME PERIOD beacon.json > proof.json
./draw-games/verifier/target/debug/draw-verify proof.json --receipt pre-draw-receipt.json

证据保存与保证范围

浏览器回执只存于当前用户、当前浏览器，最多保留 256 条、30 天；清理浏览器数据或更换设备会影响可用性，需要长期保留时请下载文件。后台彩票票据与开奖证明按现有 30 天策略清理；骰宝房间内历史最多 60 轮，账本沿用服务原有保留策略。这里没有永久保存承诺，也没有全局只追加的公开证明日志。

本地回执不是签名时间戳。验证器能检查提供的文件是否符合算法及已保存输入，不能单独证明回执何时出现、谁拥有账号、钱是否实际记入钱包、服务一定完成开奖，或线上运行了哪一个二进制。缺少开奖前回执时，只能复核文件内部的一致性；定期开奖仍可检查固定轮次签名并独立推导结果。共享种子承诺不等于服务器盲发，房间骰宝尤其保留运营方预知与中止风险。

老虎机中奖逻辑、抓娃娃物理模拟及名单抽奖目前在浏览器运行，没有相应后台开奖模块可放入本目录。它们不在本次七种后台游戏范围内。

Lottery and Sicbo: public process, independent replay

draw-games/ is a subdirectory of the existing BluffKing open-source repository. It publishes draw inputs, deterministic sampling, prize calculation, purchase cutoffs and related persistence, together with an offline verifier that needs no connection to BluffKing. It covers Sicbo, scratch cards, SSQ, Happy8, Fucai3D, Daletou and TOTO. Stakes and prizes use practice beans.

This proof protocol has not yet been deployed to production. Source publication does not switch the live protocol. Generating these proofs requires the matching backend and client version; a public tag does not attest the production binary. Historical records without proofs stay explicitly legacy: no retrospective commitments are invented.

Code uses the root AGPL-3.0-only license; see the trademark policy. The repository contains no player data, runtime keys, unrevealed seeds or actual future draw results.

Three draw flows

GameBefore the drawAfterwards and limitations
Sicbo roomsEach round fixes a server-seed commitment. It must be durable before a wager is accepted; the wager binds that commitment. A successful HTTP wager acknowledgement waits for that wager to become durable.The seed is revealed to replay all three dice. WebSocket updates may precede durable acknowledgement; a timeout means unknown acknowledgement, not rollback. There is no player seed in rooms, so the operator knows the outcome beforehand; commitment alone cannot prevent choosing among seeds beforehand or aborting a round.
Scratch cards and solo SicboObtain a durable server-seed commitment first, then generate a 32-byte player seed with browser cryptographic randomness. The request binds the commitment, player seed and purchase/wager terms. The browser saves a receipt before sending it.The revealed server seed reproduces the result and prize. A single scratch card reveals its full seed only after every spot is open; batches of 5/10 reveal immediately. The server can compute the outcome after receiving the player seed. A commitment cannot compel continued service or payment.
SSQ and other scheduled lotteriesA fixed plan binds the game, period, protocol version, sales cutoff, drand chain and future round. A purchase must echo the observed plan commitment; its ticket retains that plan.Verify the selected round's BLS signature and derive numbers using the published algorithm. There is no selectable server seed. An outage waits for that exact round, with no substitute round or OS-random fallback. Anyone with its public beacon can reconstruct the result even if the operator withholds it.

Fixed scheduled-draw inputs

SSQ, Daletou and TOTO draw every five minutes, with Daletou offset by 75 seconds and TOTO by 150 seconds. Happy8 draws every two minutes, Fucai3D every three. Sales close five seconds before the planned draw, with period labels in Singapore time. The plan selects the first drand quicknet round scheduled at or after draw time, never the relay's “latest” round.

The pinned chain is 52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971, with genesis Unix second 1692803367 and a three-second period. beacon.rs pins its public key and verifies the bls-unchained-g1-rfc9380 signature. Randomness is SHA-256(signature); the relay's supplied randomness field is not trusted.

lottery.rs binds the plan commitment to beacon randomness. proof.rs specifies domain-separated, length-prefixed SHA-256 inputs and a counter stream. Rejection sampling removes modulo bias; partial Fisher–Yates samples without replacement. Beacon unpredictability and availability still depend on threshold participants and timing assumptions: see the drand security model. Signature verification uses pinned drand-verify 0.6.2.

Beacon requests have timeouts, response-size limits and retry spacing, and run outside database transactions and row locks. If the selected beacon cannot be obtained or verified, the same draw remains pending. Persistence constraints protect published plans and completed results; retries and recovery do not choose another result. Pre-existing legacy periods finish under their original path and remain without proofs.

Numbers and prize rules

SicboThree independent dice in 1–6. Small is 4–10, big is 11–17, and triples lose both bets. Solo and rooms share the same rules.
Scratch cardsSix numbers and one lucky number independently drawn from 1–30; matching positions pay multipliers 1, 1, 2, 2, 5, 10, added together. Results are stored at purchase and unopened numbers are hidden from responses. See scratch.rs.
SSQSix distinct red balls from 1–33 and one independent blue ball from 1–16.
Happy8Twenty distinct numbers from 1–80.
Fucai3DThree independent digits from 0–9; straight, group-three and group-six entries.
DaletouFive distinct front numbers from 1–35 and two independently sampled distinct back numbers from 1–12.
TOTOSeven distinct numbers from 1–49; the first six are main numbers and the seventh is additional.

Scheduled-game normalization, system-entry stake counts, multipliers, costs and complete practice-bean prize tables are in lottery.rs. Both the backend in this snapshot and the offline verifier depend on that same library.

Independent verification

Build the independent verifier from the public repository root. An initial build may download locked dependencies; running the verifier is network-free and needs neither a database nor a BluffKing account.

cargo build --locked --manifest-path draw-games/verifier/Cargo.toml
./draw-games/verifier/target/debug/draw-verify proof.json
./draw-games/verifier/target/debug/draw-verify proof.json --receipt pre-draw-receipt.json
  1. Save the pre-bet commitment receipt in the matching client, then download the proof after the draw. The client can export a {proof, receipt} bundle; separate proof and previously saved receipt files also work.
  2. The verifier reconstructs numbers or dice and, when wager/ticket details are present, recomputes costs and prizes. A supplied receipt is compared with the original commitment, player seed and applicable wager terms.
  3. Success reports outcome: "replayed". receipt_match is "matched" for a matching receipt or "not_provided" when none was supplied. A mismatch or invalid proof reports "rejected" and exits with code 1. Successful replay alone does not establish possession of pre-draw evidence.

Scheduled draws expose account-free GET /api/draws/:game/:period/proof, returning plan, proof and proof_status: pending, available or legacy. This endpoint exposes no private selections or account data. A personal history ticket can be attached as the proof's ticket field to check its prize calculation.

If the operator withholds its proof, obtain the exact round from the saved plan at https://api.drand.sh/52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971/public/{round} and save it as beacon.json. Replace GAME and PERIOD below with the saved game's name and integer period. The command verifies the round and signature, then emits a complete draw proof.

./draw-games/verifier/target/debug/draw-verify --derive-lottery GAME PERIOD beacon.json > proof.json
./draw-games/verifier/target/debug/draw-verify proof.json --receipt pre-draw-receipt.json

Evidence retention and guarantees

Browser receipts belong to the current user in that browser, with limits of 256 entries and 30 days. Clearing browser storage or changing devices affects availability; download files for longer retention. Server lottery tickets and draw proofs follow the existing 30-day cleanup policy. Sicbo room history retains up to 60 rounds; ledger records follow the service's existing retention policy. This is neither permanent evidence storage nor a global append-only public proof log.

A local receipt is not a signed timestamp. Verification checks the supplied data against the algorithm and saved inputs; it cannot alone prove publication time, account ownership, actual wallet credit, eventual service completion or the deployed binary. Without a pre-bet receipt, verification is unanchored to an earlier observation; scheduled results still have a verifiable fixed-round beacon and can be derived independently. Seed commitments are not server-blind dealing: room Sicbo retains operator preknowledge and abort risk.

Slots prize logic, Claw physics and the name picker currently run in the browser. There are no corresponding backend draw modules to include here; these features are outside the seven backend games covered by this publication.
